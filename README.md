# Purrfect 🐾 — дневник любимца

**Версия v1.3 (Мастер слияния — безопасное объединение заметок, бета).** Мобильный PWA для ухода за питомцами: профиль, дневник, календарь, вет-помощник и общие семейные записи через Firebase.

## v1.3 — «Мастер слияния» (бета, требуется ручной тест)
- В семейной панели при конфликте есть «Посмотреть слияние заметок»: показывает локальные заметки, которых ещё нет в облаке.
- Выявляет одинаковые ID с разным содержимым и заметки с неизвестным питомцем; такие случаи блокируют этот простой сценарий.
- Только после подтверждения выполняется транзакция Firestore с повторной проверкой исходной ревизии; при изменении ревизии слияние останавливается без потери локальной копии.
- Объединяются **только новые заметки**. Удаления, изменения существующих заметок, еда, другие коллекции и общие настройки не объединяются и остаются предметом будущего полноценного merge. Пользователь должен хранить резервные копии, особенно если локальные отличия других типов важны.
- Это не сквозное восстановление всех конфликтов. После merge итоговая облачная база загружается локально на этом устройстве, поэтому копию перед объединением сохранять обязательно.
- Новых правил Firebase не требуется: используется revision-транзакция из v1.2.

## v1.2 — «Призрак конфликтов» (нужен тест)
- При сохранении семейного документа Firestore используется транзакция с проверкой поля `revision`.
- Если другая вкладка/участник изменили базу после последнего чтения, устаревшая версия **не отправляется**, а локальные записи остаются на устройстве.
- В семейной панели показывается сообщение о конфликте и две опции: скачать локальный бэкап и осознанно загрузить облачную версию.
- Отметка о локальных несохранённых изменениях хранится в localStorage и переживает перезагрузку вкладки.
- Данные по-прежнему лежат в одном общем Firestore-документе. **Слияния конфликтующих изменений пока нет**: для одновременной полноценной работы нужна следующая итерация — отдельные документы и стратегия merge.
- **ОБЯЗАТЕЛЬНО** обновить Firestore Security Rules из файла `firestore.rules` в Firebase Console → Firestore Database → Rules → Publish. До этого обновлённый клиент не сможет записывать поле `revision` (permission-denied). Старые вкладки после публикации правил могут перестать записывать, их необходимо перезагрузить.
- Перед первым тестом скачать резервную копию на обеих тестовых устройствах. На продакшен-семье не устраивать эксперимент с одновременной перезаписью до проверки.
- На уровне кодовой проверки подтверждён синтаксис; **сквозные многопользовательские тесты с настоящим Firebase ещё не проведены**.

## v1.1.3 — очистка смешанного письма OCR
- Исправлена очистка ошибочного заголовка `RHE COCTAB:`, где `COCTAB` содержит латинские буквы, похожие на кириллицу.
- Проверены смешанные написания `RHE СОСТАВ`, `СОСТАВ`, `CОCТАB`; обычные названия ингредиентов не изменяются.
- Очистка выполняется в форме, для изменения сохранённой карточки по-прежнему нужно нажать «Сохранить изменения».

## v1.1.2 — безопасный импорт этикеток
- Если OCR распознал ингредиенты, но не распознал аналитические компоненты, об этом сообщается явно; другие поля не перезаписываются.
- Отдельная кнопка «Очистить состав от заголовков и добавок» помогает поправить ранее сохранённый OCR-текст. Изменение вступает в силу только после сохранения карточки.
- Парсер разделов и очистка проверены на примерах с переносами строк и OCR-мусором «RHE». Ни один алгоритм не заменяет визуальную сверку с упаковкой.

## v1.1.1 — исправление распознавания разделов
- OCR-текст с переносами строк разделяется по заголовкам «СОСТАВ / ИНГРЕДИЕНТЫ», «ДОБАВКИ», «СОДЕРЖАНИЕ ПИТАТЕЛЬНЫХ ВЕЩЕСТВ / АНАЛИТИЧЕСКИЕ КОМПОНЕНТЫ».
- Добавки не примешиваются автоматически к ингредиентам; оригинальный OCR-текст остаётся доступным для ручной проверки.
- Если заголовков нет, распознаются только явно подписанные проценты, а непонятные поля не перезаписываются.
- Важно: ранее вручную сохранённые неточные данные не изменяются без участия пользователя.

## v1.1 — Умная упаковка (первый этап)
- Редактирование существующей карточки корма без изменения ID; привязанные реакции сохраняются.
- Источник корма по ссылке http(s), отображение домена в карточке. Сама страница **не скачивается** — маркетплейсы обычно запрещают прямое чтение из браузера (CORS).
- Добавление изображения этикетки с OCR для русского и английского. Распознавание запускается в браузере через Tesseract.js 5.1.1, загружаемый по требованию с jsDelivr, вместе с языковыми файлами. Первый запуск требует интернет и может быть долгим; в офлайне при первом запуске OCR недоступен.
- Распознанный текст предлагается для переноса в поля ингредиентов и процентов, без автоматического сохранения; проверка вручную обязательна.
- OCR может ошибаться в цифрах, буквах и разделении текста; не предназначен для медицинских выводов.
- Фото не добавляется в записи и не загружается в Firebase приложением; OCR выполняется на устройстве, а для скачивания модели используются сторонние ресурсы.
- Для маркетплейсов возможен временный путь: скопировать описание со страницы → вставить в «Умную упаковку» → проверить → сохранить.
- В будущем: полноценный серверный импорт по ссылке с законными источниками и проверкой происхождения данных.

## v1.0 — Smart Nutrition 2.0 (экспериментальный разбор)
- Из текста аналитических компонентов извлекаются проценты белка, жира, клетчатки, золы, влажности, омега-3/6, кальция и фосфора (при распознанных названиях с символом %).
- Таблица показывает исходные значения и, если известна влажность менее 100%, расчёт на сухое вещество.
- Неизвестная влажность не оценивается по типу корма; при ней в сухом веществе выводится прочерк.
- Повторные противоречивые показатели скрываются с предупреждением. Данные этикетки проверяются вручную.
- Никаких медицинских оценок качества корма или рекомендаций по лечебным диетам по этим цифрам. Проценты могут быть округлены, иметь границы минимум/максимум.
- Изменения применяются к старым карточкам без миграции данных — заново вносить ранее введённый состав не нужно.

## Обязательно перед тестом новых ролей
**Замените правила Firestore** в Firebase Console → Firestore Database → Rules точным содержимым файла [firestore.rules](./firestore.rules) и нажмите Publish. Коммит кода на GitHub сам по себе НЕ обновляет опубликованные правила Firestore. Без этого новые кнопки управления семьёй могут отвечать ошибкой permission-denied.

Сначала протестируйте функции на тестовой семье, не на настоящих данных.

## Ограничения
- Почтовая ссылка-приглашение только заполняет ID семьи; владелец должен отдельно добавить UID нового участника.
- Синхронизация пока перезаписывает один общий документ целиком; параллельные правки могут конфликтовать. Не используйте как готовое коммерческое решение.
- В интерфейсе пока показаны ID участников, а не их адреса и имена — данные чужих Firebase Auth-аккаунтов не раскрываются.
- Отзыв доступа запрещает дальнейшие облачные операции, но не стирает ранее загруженные локальные данные с чужого устройства.
- Сначала скачивайте резервную копию через «Ещё → Скачать резервную копию».
- Firebase Admin SDK, приватные ключи, пароли и личные резервные копии не добавлять в публичный репозиторий.
