# 🏰 Purrfect v1.5 — «Монолит единой базы», архитектурный рейд

**Статус: экспериментальная фаза. Продакшен НЕ мигрирован.**

## 🪞 Фаза 2 — «Зеркальное королевство» (безопасный стенд)
- [Демо с синтетическими данными](./index.html) работает в браузере **только в памяти**, Firebase не подключается.
- `synthetic-family.json` — вымышленные записи: один питомец, две заметки, один вес, одна отметка удаления.
- `mirror-demo.js` разбивает данные на отдельные записи и сверяет точное содержимое по пути и количеству.
- `test-firestore.rules` — пример изолированных правил для **отдельного тестового Firebase-проекта**. НЕ публиковать их в рабочем проекте Purrfect.
- Тестовое приложение пока **не записывает в Firestore**. Правила не проверены эмулятором; до развёртывания необходим тест Firebase Rules Emulator.
- Следующий шаг: создать отдельный проект Firebase с тестовыми аккаунтами и подключить проверяемый импорт исключительно искусственных данных.

## 🔐 Фаза 3 — браузерный портал реального тестового Firestore
- [Лабораторный портал](./lab.html) принимает вручную **только публичные Web App API key и App ID** от проекта `purrfect-lab`. Имя проекта намеренно зафиксировано в коде.
- Email и пароль применяются для входа в отдельную Firebase Authentication лаборатории. Пароль не коммитится в GitHub и очищается из формы после авторизации; Firebase SDK может сохранять сессию.
- Тестовая семья создаётся как `families/mirror-<UID>` только для вошедшего пользователя; данные берутся исключительно из `synthetic-family.json`.
- Запись пяти тестовых документов выполняется отдельными запросами без удаления и обновления. При несовпадении уже существующего документа запись останавливается.
- После записи выполняется отдельная проверка каждого документа. Возможна частичная запись при ошибке соединения; повторный запуск идемпотентен для идентичных данных.
- Используется опубликенный в **отдельной** лаборатории файл `test-firestore.rules`. Права на редактирование и удаление в этом испытании не нужны.
- Не вводить в портал рабочие конфигурации, личные записи питомцев или служебные Firebase Admin credentials.
- Код подготовлен; браузерная работа с лабораторным Firebase требует ручного подтверждения.

## Текущая схема
`families/{familyId}/shared/state` — один документ со всеми данными, ревизией и проверкой в транзакции. В рабочей v1.4.1 при конфликте есть выборочное слияние новых заметок.

## Кандидат новой схемы (не развёрнут)
- `families/{fid}/pets/{petId}` — каждый питомец отдельно
- `families/{fid}/records/notes/items/{id}` — заметка
- `families/{fid}/records/weights/items/{id}` — измерение веса
- Аналогично для `events`, `vaccines`, `foods`, `shopping`, `visits`, `foodReactions`
- `families/{fid}/records/noteTombstones/items/{id}` — отметки об удалении заметок
- `families/{fid}/meta/migration` — служебный статус переноса, исходная ревизия, схема и контрольные суммы (будущий этап)

**Важно:** промежуточные документы `records/{kind}` не обязаны существовать; подколлекции `items` могут существовать независимо. Будущие запросы потребуют соответствующих индексов и Security Rules.

## Что сделано
- `record-migration.js` строит план, **не записывая ничего** в Firebase, браузер или localStorage
- Проверяет ID, дубликаты, ссылки на питомца, формат коллекций, отметки удаления и конфликт активной/удалённой записи
- Сохраняет идентичность ID и создаёт отдельные пути записей для дальнейшего ручного переноса
- Требует подтверждённую ревизию серверного снимка, чтобы не превращать устаревшие локальные данные в источник истины
- `record-migration.test.mjs` — воспроизводимые тесты через Node.js

## Барьеры безопасности до запуска записи
1. Создать **отдельный тестовый Firebase-проект**; не менять правила реального Purrfect во время архитектурных тестов.
2. Написать правила доступа: только участники соответствующей семьи, допустимые коллекции и пути, ограничение размеров и набора полей.
3. Реализовать идемпотентный shadow-import из подтверждённого серверного снимка с фиксацией ревизии и контрольной суммы. Учитывать пределы размера, число операций и стоимость Firestore.
4. Двойное чтение и сравнение результатов новой модели со старым документом, **без двойной записи из рабочего приложения**.
5. Проверить два аккаунта: параллельное добавление, исправление, удаление, офлайн, повторные подключения и восстановление резервной копии.
6. Только после тестов сделать переключатель нового режима с откатом; все изменения записываются в roadmap.

### Известные ограничения
Это пока **планировщик**, а не мигратор. Он не анализирует семантику изменений полей, не проверяет фотографии/base64 и не гарантирует, что вся база помещается в квоты нового хранилища. Документ `settings`, `active` и прочие верхнеуровневые поля требуют отдельного проектирования. Удаления для других коллекций ещё не имеют tombstones.
